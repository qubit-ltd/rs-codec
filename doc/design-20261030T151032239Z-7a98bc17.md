## 现状与依据

### RC-R2-001：覆盖率证据过期

`coverage-summary.md` 顶部显示 95.3% 行覆盖率，但其中 `AsyncTranscodeDecodeInput::transcode_eof_step` 的源码仍包含 unread 为空时直接返回的旧分支，并使用普通 `validate_decode_progress`。当前 `src/transcode/io/async_transcode_decode_input.rs` 会派发空输入 EOF，并调用 `validate_eof_decode_progress`。报告中的 converter 生命周期缓冲分配也早于当前 `try_reserve_vec` 路径。因此旧比例不能证明当前路径已被覆盖，亦不能据此推断当前测试不足。

### RC-R2-002：设计文档的边界混淆

`doc/transcode_error_refactor_design.zh_CN.md` 的进度错误说明及转换表把缓冲 driver 统一描述为返回方向错误。实际 `src/transcode/io/internal/transcode_progress_validation.rs` 将契约错误直接装入 `io::Error(InvalidData)`；`Transcoder::transcode_complete_into` 的默认实现才有转换为 `TranscodeFailure::InvalidProgress` 再经方向错误承载的路径。

`doc/decode_lifecycle_output_design.zh_CN.md` 把两个 owned lifecycle 入口都描述成拒绝尾随输入。实际 value 入口校验完整切片恰好编码一个值；I/O 入口按 `CodecDecodeDriver::accept` 消费一个值，保留后续 unread 数据，支持连续读取。

### RC-R2-003：Rustdoc 漏述

`src/transcode/engine/transcode_decode_hooks.rs` 的 `handle_incomplete_decode` 文档只提及短尾部导致 `source = None`。codec 已调用但返回 `DecodeFailure::incomplete(...)` 时同样没有 source。`doc/user_guide.md` 和 `doc/user_guide.zh_CN.md` 已正确解释两种情况，可直接作为语义参照。

### RC-009：基准证据不足

`benches/transcode.rs` 的 `direct_transcode`、`complete_lifecycle`、`decode_engine`、`codec_adapter`、`output_window_32`、`output_window_1024` 未统一观察每次完整写出区域；有的仅观察进度，有的仅观察首字节。`benches/README.md` 已有多轮审计，仍将六条路径列为 `Unresolved`。不能从这些事实直接推出优化器确实移除了写入。

### 一、准确区分错误与消费边界

错误设计文档使用下表替换笼统的 driver 说明，并同步修改现有转换关系表：

| 调用边界 | 契约错误的实际形状 | 消费与恢复说明 |
| --- | --- | --- |
| 直接调用 `TranscodeProgress::validate` | `Result<(), TranscodeContractError>` | 校验本身不回滚已经发生的操作 |
| `Transcoder::transcode_complete_into` 默认驱动 | `TranscodeFailure::InvalidProgress`，再通过 `Self::Error: From<TranscodeFailure>` 包装 | 错误不意味着 codec 或输出已回滚 |
| 同步／异步 I/O 的进度校验 | `io::Error`，kind 为 `InvalidData`，source 为 `TranscodeContractError` | 成功校验后才提交本次进度的输入消费或输出 advance；失败不回滚 decoder/encoder 内部状态和已经写入的调用方存储 |
| EOF 后仍返回 `NeedInput` | I/O 层返回 `InvalidData`，该语义错误不必具有 `TranscodeContractError` source | 不提交该步输入消费，不能承诺通用重放 |

生命周期设计文档分开说明：

- `CodecValueDecoder::decode_lifecycle(input)`：完整切片应恰好表示一个主体值，额外 unit 返回 `TrailingInput`。
- `TranscodeDecodeInput::read_decoded_lifecycle_with(...)`：从连续输入读取一个主体值并消费其单位数；之后的数据保留给下一次读取，不因存在后续值而返回 `TrailingInput`。reset/finish 是本次单值调用的生命周期，不改成整条 I/O 流的生命周期。

只修正现有两份中文设计文档中的相关段落和表格。不新建英文设计译本，也不整体改写已基本一致的 README、用户指南。生产实现及下游调用无需迁移。

### 二、补齐 Rustdoc

在 `handle_incomplete_decode` 的说明中明确 `Some(source)` 仅来自携带 source 的 incomplete failure，`None` 有两种来源：

1. 尾部短于 `MIN_UNITS_PER_VALUE`，引擎未调用 codec。
2. codec 已调用，但返回不携带 source 的 `DecodeFailure::incomplete(...)`。

保留现有容量预检、消费整个尾部、converter pending 保留等说明。生产 Rustdoc 使用英文；不修改函数签名或行为。已有示例和测试足以承载此文档修正，不为措辞调整新增重复测试。

### 三、覆盖率报告的可追溯生成

使用现有 `./.infra/bin/coverage.sh` 入口，先阅读其实际执行器和参数，沿用当前 crate 的配置。不得在未检查执行器前臆测其 feature 集、清理范围或输出文件名。正常清理可重新生成的 coverage 产物属于流程范围；不得扩展清理至源码、配置或用户数据。

先完成本轮 Rustdoc 及任何已确认必要的基准修正，再生成最终报告。保留现有 coverage 阈值和豁免配置，不通过降低阈值、扩大豁免或增加生产 coverage cfg 使报告通过。

在 `coverage-summary.md` 头部增加紧凑的生成信息：

- 实际生成时间、源码基线提交和工作区是否含未提交变化。
- 源码快照摘要：按仓库相对路径排序，对 `src/**/*.rs`、`tests/**/*.rs`、`examples/**/*.rs`、`benches/**/*.rs`、`Cargo.toml`、`Cargo.lock`、`rust-toolchain.toml`、`.infra/coverage/coverage.json` 和 `.infra/ci/cargo-matrix.json` 逐文件计算 SHA-256，再汇总路径与摘要；排除报告自身以避免自引用。
- `rustc -Vv`、实际 coverage 工具／执行器版本、精确命令、实际 feature 配置、运行退出码。
- 本次 HTML／LCOV 及 badge 的实际位置；本地生成不能冒充已上传的 CI artifact。为便于独立理解，同时记录当前关键 EOF 与分配路径对应的覆盖情况。

全量逐文件摘要清单放在本次构建产物目录，摘要算法、汇总值和清单位置写入报告。最终报告不依赖只有临时工作树中存在的源码路径作为唯一证据；源码路径按当前实际仓库关联，并注明生成环境。

若覆盖率执行失败或发现真实测试缺口，如实记录失败和未覆盖路径；只在能够指出与本轮 EOF／分配验证目标相关的具体行为缺口时补充针对性测试。与本轮无关的失败另列，不静默修复或宣称已通过。

### 四、RC-009 核查与条件修正

先建立六条路径的逐项证据表，记录源码范围、64 KiB 输入、每次写出范围、32／1024 窗口循环次数、当前观察点和预期数据移动量。默认 bench profile 为 `opt-level=3`、`lto=true`、`codegen-units=1`，保持不变。

至多进行一轮当前默认 profile 构建，并在确有新归属方法时增加一次辅助归属分析；若源码、工具链及默认产物的机器码与既有审计一致且没有新证据，复用其限制结论，不重复构建。记录命令、工具链、CPU／目标平台、artifact 路径及 SHA-256，并保存完整构建日志及 `nm`、`objdump` 输出至可再生成的构建产物目录。辅助构建只能辅助定位，不能替代默认 profile 的结论。

每条路径必须归入以下一种结果：

| 结果 | 处理 |
| --- | --- |
| 默认产物可归属，完整写入确实保留 | 保留基准源码，记录可归属指令／循环覆盖的完整输出范围 |
| 默认产物可归属，确认部分或全部写入被消除 | 仅修正相应基准的观察方式，再构建核对完整写入并重新测量 |
| 默认产物仍无法归属或不足以判断 | 保持 `Unresolved`，记录限制和停止原因；不据此修正源码或发布性能结论 |

若确认需要修正，完整输出路径在每次计时调用后观察 `&output[..written]`；窗口路径在下一次覆盖前观察该窗口的 `&output[..progress.written()]`。保留计数观察用于进度校验，不把 checksum 计算加入计时主路径，不改变生产函数内联策略。使用原有完整输出观察 helper 的模式；不扩展 benchmark harness 的公共接口。修正后的测量建立新基线，不能将测量构造变化解释为生产库性能提升。

更新 `benches/README.md` 中 RC-009 的当前结论并保留历史记录；每条路径单独判定。证据不足允许结束本次核查，但不允许把 RC-009 标记为已修复或已证明不存在问题。

## 验收与风险

- 三项已确认意见分别有文档或当前报告的直接证据，不以“文件已改”代替内容核对。
- value 与 I/O 的尾随输入和消费语义明确；I/O 进度错误的 source 类型说明准确。

- 现有工具若更新了不相关项目文件，应先检查原因并保留用户工作，不能为收敛 diff 自动丢弃变更。
- 主要风险是 coverage 执行器的真实参数／产物与旧报告不同，以及 LTO 继续使基准归属困难；均以真实输出记录，不虚构结果或扩大改造。
